# Northordo — правила разработки

## Цель и текущая стадия

Northordo — закрытая внутренняя веб-система для ремонтного бизнеса семьи. Это не публичный сайт и не сервис для сторонних компаний. Реализованы локальная оболочка React + TypeScript + Vite, начальная авторизация OWNER/ADMIN и модули объектов, смет, работ, финансов, материалов, инструментов и документов. Управление пользователями и резервное копирование ещё не реализованы. Исходный код открыт, рабочие данные остаются закрытыми.

Перед изменением архитектуры сверяйся с [предложением по архитектуре](docs/architecture.md). Оно остаётся предложением, пока владелец не примет решения, отмеченные в разделе вопросов.

## Обязательные ограничения

- Рабочая платформа разработки — Windows. Приводи команды для PowerShell, если пользователь должен запускать их вручную.
- Предпочтительный клиентский стек: React, TypeScript и Vite. Новые зависимости добавляй только при явной технической необходимости; не добавляй платные API или обязательные подписки.
- Не подключай облачные сервисы, внешнее хранилище, аналитику или стороннюю авторизацию без отдельного решения владельца.
- Не загружай и не копируй реальные документы компании. Сейчас документы остаются на компьютере отца. Не добавляй реальные клиентские, финансовые или учётные данные в код, фикстуры, логи или репозиторий.
- Требование владельца: нужен ограниченный удалённый доступ через интернет. Не открывай текущий Vite dev-сервер в сеть, не меняй его loopback-привязку и не настраивай проброс портов. Сначала реализуй и проверь серверную авторизацию, права OWNER/ADMIN, HTTPS/VPN и защиту хоста; база данных не должна быть доступна извне.
- Не выдавай макет, стартовые данные или клиентскую проверку интерфейса за работающую серверную функциональность или защиту.

## Роли и безопасность

В продукте ровно две роли: `OWNER` и `ADMIN`. Не вводи дополнительные роли и не позволяй ADMIN повышать собственные права.

- OWNER управляет пользователями, приглашениями, блокировками, назначением ADMIN и критическими настройками безопасности.
- ADMIN работает с рабочими модулями, но не управляет пользователями и привилегиями.
- Когда появится сервер, он должен проверять каждый доступ и каждое изменение данных. Скрытые кнопки и проверки только в React не являются контролем доступа.
- До появления серверной авторизации не сохраняй чувствительные данные в браузере и не реализуй фиктивную авторизацию.
- Для документов сначала проектируй безопасное локальное связывание и выдачу файлов. Не принимай абсолютный путь от клиента как доверенный ввод и не допускай выхода за разрешённую папку хранения.
- Секреты не помещай в клиентский код, Git или документацию. Важные изменения должны журналироваться без записи паролей, токенов и содержимого документов.

## Структура и качество работы

- Развивай систему по этапам; сначала зафиксируй архитектурные решения, затем создавай соответствующие модули.
- Держи продуктовые области (объекты, сметы, финансы, материалы, инструменты, документы) раздельными модулями. Не связывай их через случайные глобальные состояния.
- Веди документацию в `docs/` и обновляй её при изменении принятых решений.
- После изменений кода проверяй доступную сборку (`npm run build`) и сообщай, что именно было проверено. Не утверждай, что безопасность проверена полностью без отдельного аудита.
- Не добавляй реальные данные для демонстрации. Если для интерфейса понадобятся фиктивные примеры, явно обозначай их как тестовые и используй вымышленные значения.
